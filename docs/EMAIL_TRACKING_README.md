# Email Tracking: Gmail extension

## Gmail extension

Click the LeadsGhr icon in Chrome's toolbar to open a compact popup. **Tracking report** shows locally stored message counts, total observed image loads, up to three recent messages, and a Refresh counts action. Each message reads, for example, **1 image load observed** with the last observed time; select a message with loads to expand its observed-load history. **Settings** lets you turn tracking on or off by default for Gmail drafts, turn image-load notifications on or off, and shows whether an endpoint and registration key are present. **Open full settings** opens the page for the public HTTPS endpoint and registration key, followed by the **Email report**: totals (tracked, opened, not opened yet, observed loads), a subject/recipient search, All / Opened / Not opened yet filters, and one row per tracked email with its status (Sent, Opened, Not sent) and load count. Selecting a row shows the send time, recipients, first load and how long after sending it happened, last load, observed-load count, tracking ID, and the load timeline. Each email has its own unique tracking pixel; an email sent to several recipients shares one pixel, so the report notes that a load can come from any of them. The popup does not add campaigns or other features from the visual reference. The preference is stored in Chrome and updates the Gmail compose control; an individual draft can still be toggled separately.

Selecting **Email Tracking** in the desktop sidebar opens the extension page directly; **Download extension ZIP** saves the ZIP. The save dialog opens in `C:\LeadsGhr\extensions`. Extract the ZIP to `C:\LeadsGhr\extensions\leadsghr-mail-tracking`, open `chrome://extensions`, enable **Developer mode**, select **Load unpacked**, and choose that folder. For updates, extract into the same folder and select **Reload**: Chrome ties an unpacked extension's ID, and therefore its saved settings and records, to the folder path. The same build artifact is at `apps/extension/leadsghr-mail-tracking.zip`.

The Email Tracking page (`packages/app/src/email-tracking-page.tsx`) has no back button. It shows: a hero with **Download extension ZIP**, which reports the saved path or cancellation; **Install in Chrome**, four cards for Download, Extract, Load in Chrome (Developer mode, Load unpacked, pin), and Connect (endpoint and registration key in full settings, then reload Gmail); an **Updating the extension** note (extract into the same folder and select Reload to keep settings and records); **How tracking works**, a four-step flow from compose to notification; **Reading the ticks in Sent**, a legend for the gray, first-purple, and both-purple states plus pointers to the hover card and Email report; and **Good to know**, covering image loads versus reads, Gmail caching, shared pixels for multiple recipients, emails sent by other tools, and what is stored online.

This is an MV3 extension for Gmail. Every compose area shows a LeadsGhr tracking indicator and an on/off control: the New message window, a popped-out reply, and the inline reply box inside a conversation. A compose area is found as the smallest element holding both a message body and a Send button. Each sent message, including every reply in a thread, gets its own tracking pixel and its own record. A reply's subject is the conversation subject prefixed with `Re:`; its recipient comes from the reply's recipient chips, or, when those are collapsed, from the other participants in the conversation. When tracking is on, clicking Gmail **Send** registers an opaque UUID, inserts a 1×1 image into the message, and then sends it. While the extension is enabled, Gmail's Sent rows show a thin double-check mark before the recipient. Both ticks are gray by default, including messages not sent with LeadsGhr tracking. When a tracked send is confirmed, the first tick turns purple (the LeadsGhr primary colour). When an image load is observed, both ticks are purple. Inside an open conversation, each message you sent shows the same ticks beside its time, so each message in a thread has its own status. An expanded message is identified exactly by the LeadsGhr pixel in its body; a collapsed message is matched by conversation subject (ignoring `Re:`/`Fwd:`) and send time within three minutes. Your untracked messages show gray ticks; other people's messages show none. Hovering, clicking, or focusing the ticks (Tab, then Enter) opens a details card without opening the conversation. For a loaded message it shows the recipient, "Opened or image loaded N minutes ago", how long after sending the first load happened, the observed-load count, a note that Gmail's image cache can hide repeat opens, and **View in LeadsGhr**, which opens the full settings page with that email expanded in the Email report. Individual load times appear only in the report, not in the card. Unloaded messages show how long ago they were sent; untracked rows say they are not tracked by LeadsGhr. Escape, scrolling, or moving the pointer away closes the card. Gray ticks on an untracked message do not imply that it was sent with tracking. The LeadsGhr logo sits beside Gmail's top-right Settings control and opens the full extension settings page. Recipient, subject, and sent time are stored in the Chrome profile, not the online tracking table. A Sent row is matched to a tracked message by subject (ignoring `Re:`/`Fwd:` prefixes, so a conversation row can match its latest tracked reply), by recipient address (from the `email` attribute Gmail puts on the row's participant names), and by the send time in the row's date tooltip (closest within three minutes). Each tracked message is given to at most one row. Emails with the same subject and body sent seconds apart to different people therefore show their own ticks and counts; a row whose time cannot be read is matched only when its subject is unique. Emails sent by another tool (mail merge, Gmail API, an outside sender) never pass through the LeadsGhr compose control, carry no LeadsGhr pixel, and show gray ticks. Two tracked emails to the same recipient with the same subject in the same minute cannot be told apart in the Sent list, although each keeps its own pixel and count in the report. Opening a card also requests fresh counts (at most every 20 seconds). Gmail DOM changes may break placement or row matching; sending is blocked if pixel registration fails, and the user can turn tracking off to send normally.

### Observed loads, history, and notifications

Gmail fetches a tracking image through Google's image proxy and may reuse its cached copy on later opens. The endpoint therefore sees only the requests that actually reach it, so the extension reports **observed image loads** ("1 image load observed", "3 image loads observed"), never an exact count of times a person opened or read the message. Commercial tools have the same limit.

- **Observed-load count** increases whenever the endpoint receives another pixel request for an armed token.
- **Timestamp history:** migration `supabase/migrations/0003_mail_tracking_events.sql` adds `mail_tracking_events`, which stores one row per observed request with only the opaque pixel ID and a timestamp. The function returns the first and last observed times and the 50 most recent timestamps. The popup and full settings page show this history. Loads recorded before the migration have no per-load timestamps.
- **Instant notifications:** every pixel request makes the tracking function send a Supabase Realtime broadcast (REST `realtime/v1/api/broadcast`) carrying only the opaque pixel ID and a time. The extension's background worker keeps a Realtime WebSocket open to a topic derived from a SHA-256 hash of the registration key (it fetches the project URL, public anon key, and topic from the function with `?realtime=1`, authenticated by the key). A broadcast triggers a refresh 0.4 s later, so a notification normally appears within a couple of seconds of the open. Socket heartbeats every 20 s keep the MV3 worker alive; the connection reconnects with backoff after a drop. If Realtime is unavailable, the worker falls back to polling every 30 seconds (Chrome's minimum alarm period) and on Refresh counts. No new secret is needed: Edge Functions receive `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` automatically, and Realtime is enabled by default in Supabase projects. Unlike Mailsuite's free plan, LeadsGhr adds no visible "sender notified" footer; recipients see nothing but the invisible 1×1 image. When a sent message gains new observed loads, Chrome shows a notification: the first one says the message "was opened or its tracking image was loaded"; later ones say "Tracking image loaded again" with the new observed total. Several loads between polls produce one notification with the current total. Clicking a notification opens the full settings page with that email expanded and scrolled into view. Notifications are on by default and can be turned off in the popup's **Settings** tab. Messages tracked before this change start at their current count without backlog alerts.
- A recipient open served from Gmail's cache produces no request, so it causes no count increase and no notification.
- **The sender's own views are not counted.** Each tracked email stores the Gmail account that sent it (read from the Gmail tab title). When that same account displays the email, for example in Sent, the Gmail script sees the proxied tracking image and records an own view. During refresh, a server load from 15 seconds before to 45 seconds after an own view is treated as the sender's and removed from the count, the load list, first and last load times, and notifications. The same email opened in a different Gmail account, even in another tab of the same Chrome profile, still counts. A real recipient open that lands inside that window can be discounted. Emails tracked before this change have no stored sender, so own views are not recognised for them.
- **A load can still appear without anyone opening the email.** Mail providers and security scanners sometimes fetch images automatically, and some mail apps preload them. These requests look the same as an open.

**A public HTTPS endpoint is required for real recipient opens.** The supplied Supabase migrations `supabase/migrations/0002_mail_tracking.sql` and `0003_mail_tracking_events.sql` store opaque tokens, image-load counts, and observed-load timestamps. `supabase/functions/mail-tracking/index.ts` serves the pixel and count requests. To run it, the owner must apply that migration, set a long random `MAIL_TRACKING_REGISTRATION_KEY` secret on the function, and deploy the function with JWT verification disabled as specified in `supabase/config.toml`. In extension settings, enter `https://<project>.supabase.co/functions/v1/mail-tracking` and the same registration key. The extension asks Chrome for permission to that origin when settings are saved. Do not enter the Supabase service role key in the extension. The service role stays server-side in the function environment.

After the one-time GitHub setup described in the root README's **Supabase deployment** section, pushing migration or function changes to any branch applies and deploys them automatically; only the function secret below must still be set once in the Supabase dashboard. Manual deployment requires a Supabase project and CLI login (CLI 3.x targets a local Docker database by default, so pass `--remote`). From the repository root, link the intended project, apply the migrations with `supabase db push`, set the function secret with `supabase secrets set MAIL_TRACKING_REGISTRATION_KEY=<long-random-value>`, then deploy with `supabase functions deploy mail-tracking --no-verify-jwt`. These commands change the hosted project and are for the owner to run after review; this repository change did not deploy anything. After pulling the load-history change, apply `0003_mail_tracking_events.sql` and redeploy the function; without the migration the function returns an error when counts are read. Keep the key private and give it only to Chrome profiles allowed to register tracking pixels. This single-key setup is a prototype, not per-user authentication or billing.

To test: install the extracted extension, configure its endpoint/key, reload Gmail, compose a message to an inbox you control, keep **Tracking on**, and send. Check the extension settings page for the new record. Open the received email with images enabled, wait about a minute, and select **Refresh counts**. The sent row should show the first tick purple right after sending and both ticks purple after the load, hovering them should show **1 image load observed** (or more), the settings page should show the same count, and Chrome should show a notification within a few seconds (up to 30 seconds if the realtime connection is down). Reopening the same email in Gmail often adds no further loads because of Gmail's image cache. First test the extension in an isolated Gmail account: Gmail UI changes and image proxy behavior can affect results. No real message was sent during development or automated checks.

The endpoint ignores image loads until after Gmail sends and the extension arms the token, plus a short delay to reduce compose-time false opens. Google or other mail image proxies can cache or prefetch images; therefore a load count is **image requests observed**, not a reliable unique-person or read count. If images are blocked, opens may be missed. Some Gmail layouts or send methods may not trigger the compose integration. The extension has not been manually exercised in a live Gmail session; verify a test send before relying on it.

**Gmail tabs reload automatically when the extension changes state.** Each Gmail script holds a port named `leadsghr-gmail` to the background worker. When LeadsGhr is turned off, reloaded, or updated, the port closes and the extension context disappears (`chrome.runtime.id` is undefined), so the tab reloads and drops LeadsGhr's controls and ticks; a normal service-worker restart only reconnects the port. On install, update, reload, and every worker start (which covers turning the extension back on), the worker pings each fully loaded `mail.google.com` tab and reloads any tab that does not answer, so the compose bar and ticks appear without a manual refresh. As with Mailsuite, an unsent draft open in that tab is interrupted by the reload; Gmail normally keeps it in Drafts.

Rebuild the ZIP after source changes on Windows with `pnpm.cmd build:extension`. This builds `apps/extension/dist` and archives its contents to `apps/extension/leadsghr-mail-tracking.zip`, then copies that ZIP to `C:\LeadsGhr\extensions\leadsghr-mail-tracking.zip`. Restart or reload the unpacked extension in Chrome after replacing its files.

## Retired local test

The earlier desktop **Email Tracking · Local test** (create a test record, open a loopback `127.0.0.1` preview, count the pixel load) was removed when the Gmail extension became the tracking path. Its page, IPC handlers, preload methods, schemas, and `apps/desktop/src/local-email-tracking.ts` loopback server no longer exist. The app no longer reads or writes the `local_email_tracking` table; an existing table in `leadsghr.sqlite` is left in place and untouched so no user data is deleted.
